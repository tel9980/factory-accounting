## A 组 · 权限与数据泄露（最高优先级）

### A1【严重】员工能查到任意客户的成本单价
- **位置**：`backend/index.js:4774` `/price-lookup`
- **机制**：SQL 是 `SELECT price, COALESCE(cost,0) AS cost ...`，响应带 `last_cost`，提示文案直接写「（成本 X 元）」。`STAFF_MONEY_DENY`(:469) 与 `STAFF_COST_PATHS`(:475) **都没有 price-lookup**。
- **改法**：把 `price-lookup` 加入 `STAFF_MONEY_DENY`；若员工仍需看报价，改成只返回 `price`。
- **代价**：1 行正则 + 员工端少一个功能。

### A2【严重】员工能看逐月利润、KPI 成本、净资产、保本线
- **位置**：`/trend`(:15010-15043，rows 含 cost/gross/profit + 逐月 total/avg/best/worst)、`/kpi`(:19689，响应 :19783-19788 含 mat_cost/cash_cost/profit/margin/cost_total/expense_ratio/break_even/net_worth)、`/break-even`(:19793-19820，gross_margin/break_even/var_ratio)、`/month-end`(:4224-4270，numbers 含 cost/pl.*)、`/close-precheck`(:4217-4220)、`/accruals`(:3979-3985，摊销+预提利息)、`/assets`(:20072-20083，total_cost)
- **机制**：denyStaff 是黑名单（:1412-1475），`kpi`/`trend`/`break-even`/`month-end` 都不在名单里。
- **改法**：这 6 条进 `STAFF_MONEY_DENY`；`/month-end` 若员工必须用，退一步做 scrub（抹 cost/margin/profit 字段）。
- **代价**：员工端少了这些页面，需跟用户确认哪些员工真的要看。

### A3【严重】员工能打开任意单据详情、附件和历史
- **位置**：`/credits`(:17158-17200，返回每一家客户的 total/unpaid)、`/my-work`(:5629-5699)、`/statement-batch`(:3063-3126)、`/history`(:18225-18236，`SELECT *` 含 cost 列，路径不匹配 STAFF_COST_PATHS)
- **机制**：`scopeOwn` 只在 11 处被调用、`selfOnly` 只在 8 处；新增接口默认不受作用域约束。
- **改法**：`/history`、`/credits`、`/statement-batch`、`/my-work` 加 scopeOwn；`/statement-batch` 若业务需要，改为只允许 scopeOwn 内客户。
- **代价**：中等。

### A4【严重】默认拒绝式改造（根治「忘记加正则」）
- **位置**：`backend/index.js:1556-1575`（staffScrub/costScrub 只对 JSON 响应跑、且路径黑名单）
- **改法**：改成白名单放行——只有 `STAFF_SAFE_PATHS` 里的路径原样返回，其余一律走 cost+money 脱敏；数组响应统一注入 `{staff_hidden:[...], data:[...]}`。
- **代价**：需要把现有合法接口逐个加进白名单（一次性工作量）。
- **收益**：以后新增接口默认安全，不需要每次都记得加正则。

### A5【高】check.mjs 加自动断言（防止再漏）
- **改法**：check.mjs 新增一节——把含 `cost|profit|margin|gross` 响应字段的 GET 路由全部列出，断言每条都在 `STAFF_MONEY_DENY` / `STAFF_MONEY_SCRUB` / `STAFF_COST_PATHS` 三者之一。**我已用脚本跑出当前 79 条命中清单**（`/tmp/denytest.mjs`），可以直接做成基线。
- **代价**：~60 行，一次性把现状对齐。

### A6【高】公开对账单/打印页永久有效且泄露公司收款账户
- **位置**：`:3494`（statement-print 渲染 `t.bank`）、`:1305-1322`（sigBook 签名**无时间戳**）、`:1350`（公开路径白名单）
- **机制**：签名只覆盖 (secret, book, party, type)，**没有 exp**；任何拿到链接的人可永久查看该客户全部历史单据与收款账户；链接无过期、无撤销、无访问计数。
- **改法**：`sigBook(key,bk,party,type,exp=0)` 签名串加 `|exp`，校验端 `now<exp`（默认 7 天）；公开页只显示账号尾号 4 位；加 `/revoke`。

- **代价**：老板「打印工资单给会计」的习惯要改（可保留本地生成 PDF 替代）。

### A8【高】公开写接口 quote-ack 可任意翻转报价状态
- **位置**：`:11260`（只校验签名 → `UPDATE quotes SET status=?`，无一次性 token、无留痕、无防重放）
- **改法**：accepted 状态不可回退为 rejected（除非显式 reopen）；写 `ack_at`/`ack_by`；每次确认写 audit_log；签名加 exp。

### A9【高】恢复码哈希随备份一起恢复 → 备份 = 万能钥匙
- **位置**：`:19141` restore 的 settings keep-list 含 `recover_hash/recover_lock/recover_fail/recover_code`；`:16946` book-reset KEEP_SET 也保留
- **机制**：备份文件本身能从 `/backup-get` 下载；恢复码通常抄在纸上和备份放一起 → 拿到备份 + 恢复码即可重置老板口令接管账套。
- **改法**：从 restore keep-list 与 backup 里剔除这 4 个键；恢复后强制重新生成恢复码（首次登录提示）。
- **代价**：恢复后恢复码失效，需重抄一份。

### A10【高】源码里的硬编码演示口令
- **位置**：`:787` `const DEMO_KEY='demo-look'`，`:945` 登录直接接受，`:1392` 中间件对任何账套接受
- **改法**：改为部署时随机生成写入 settings `demo_key`；未配置时演示账套不可登录（`demo_builtin_off` 字段已有）。
- **代价**：需初始化脚本；演示访问体验略变。

### A11【中】track-log 公开页无限写入 + 访客 UA 暴露
- **位置**：`:3226-3236`（每次看公开页 INSERT track_log；`/track-log` 对员工开放）
- **改法**：写入加「每 party 每小时 1 条」去重；`/track-log` 只对 owner 开放。

### A12【中】/auth/recover 把新口令明文回显 + 强度下限 4 位
- **位置**：`:1085` `return c.json({ok:true, key:pw})`、`:1081` `pw.length<4`

## B 组 · 并发与幂等

### B1【严重】批量整户收款在 >50 单时**整笔失败**
- **位置**：`backend/index.js:11519-11523`（st = N×2 条一次 db.batch）、`:11593-11598`（pay-batch 同构）
- **机制**：D1 单批上限 100 语句；51 张未结单 → 102 条 → `D1_ERROR: too many statements in batch` → **整户收款全部失败**（不是部分失败）。
- **改法**：改为逐单调用单据核销函数（每单一个事务，每单内部已有 `WHERE paid+written_off+? <= price+0.005` 条件门控 → 天然幂等），再汇总结果。
- **代价**：失去整户原子性（现状本来也是逐单门控）；延迟增加（50 单 × 1 往返）。

### B2【严重】三条路径只查不占坑 → 可重复付款
- **位置**：`:10205` `/onboarding/apply`、`:5118` `/recon-fix-batch`、`:11731` `/payables/:id/pay`
- **机制**：opSeen 是「先查后写」，并发两个请求都查不到就都执行。`/payables/:id/pay` 是**付款**路径 → 双击/双设备可付两次。
- **改法**：统一改 opClaim（占坑行与付款写入同一 db.batch 的第一条），失败返 409 或 dup_ok。

### B3【高】op_dedupe.client_id 全局唯一 → 跨业务误判重复
- **位置**：`:191-226`、schema.sql:375-382（`client_id TEXT UNIQUE`，不含 kind）
- **机制**：同一 uuid 用于两个不同操作 → 第二次 opClaim 冲突 → 返回 `{ok:true,dup_ok:true}`，**真实操作被静默丢弃**。
- **改法**：唯一键改 `UNIQUE(client_id,kind)`（迁移加索引 + 回填）；opSeen 带 kind 参数（改 12 个调用点）；冲突返回明确错误码。

### B4【高】opMark 不刷新 created_at → 7 天后幂等失效
- **位置**：`:195-200`（ON CONFLICT 只 SET kind,ref_id）、`:21299-21305`（GC 按 created_at 删 7 天前）
- **机制**：GC 依据 claim 时刻而非完成时刻 → 一周后重试同一 client_id 被当新请求 → **重复记账**。
- **改法**：opMark 刷新 created_at 或加 done_at 列；GC 只删未完成行（ref_id=-1），完成行留 30 天。

### B5【高】opRelease 只能删 ref_id=-1 的行 → 失败后该操作永久失效
- **位置**：`:224-226`；opRelease 24 处、opMark 14 处，配对不严格
- **改法**：约定 claim(-1)→成功 opMark(ref)→失败 opRelease(-1)；opRelease 放宽到 `ref_id IS NULL OR ref_id=-1`，或引入 opFail 明确标记可重试。

### B6【高】pay-batch 的预付段失败完全静默
- **位置**：`:11608-11630`（st3 失败只 noteFail，返回 ok:true 无 warn）；receive-batch(:11534) 至少提示 partial
- **改法**：pay-batch 对齐 receive-batch，返回 `warn:{code:'partial'}`。

### B7【中】批量收付的明细金额是事务外的旧值
- **位置**：`:11490-11506`（先 SELECT 全部未结单，再在 JS 算 unpaid/takeIn）
- **机制**：预读后另一笔收款已付掉该单 → SQL 条件挡住越界写入，但**返回给用户的核销金额仍是旧值**。
- **改法**：事务后用 hit/miss 比对生成 `skipped:[{id,reason}]`；detail 的金额以实际落库为准，不一致返 warn。

### B8【中】导入分片非原子 + 逐行查重 N+1
- **位置**：`:13040-13070`（每 50 条 flush，逐行 SELECT 查重）
- **机制**：导入 500 行 = 500 次查重往返 + 10 批写；第 7 批失败则前 300 行已入库无法整体撤销。
- **改法**：导入前一次拉取该月已有键集合到内存判断；按 90 条一批；每批 import_batch 标记写进 settings 供 undo 精准回滚。

### B9【中】recon-fix-batch / recon-save 中途失败留半成品
- **位置**：`:5126-5204`、`:4716-4734`
- **改法**：先跑「预检」（全部客户金额门控检查）通过再执行；失败回传 done[]/failed[]。

## C 组 · 账务口径一致性

### C1【严重】「本月净利」有 11 处实现，扣减项各不相同
- **位置**：monthPL(:413)、monthSnapshot(:4046)、report-print(:4461)、parse-import(:4631)、dashboard(:9689-9698)、weeklyStat(:9832)、profit-compare(:9920-9930)、year-customers(:12263)、customer-card(:12481)、year-summary(:14859)、month-report/books(:12342/:9294)
- **现象**：report-print / profit-compare / year-summary **都不扣坏账核销**；weeklyStat **连摊销/折旧/计提都没扣**，却在 :9849 文案里自称「净利（权责口径）」；year-customers 只扣材料成本却在 :12284 写「最赚的是…毛利」。
- **改法**：抽唯一入口 `plOf(db, mm, {includeWriteoff, includeAccrual})`，11 处全部改调它；返回值加 `basis:'cash'|'accrual'|'partial'` 标签字段。
- **代价**：改 6 个页面返回值；需回归月结页/报表页/周报/KPI。

### C2【严重】坏账核销的月份归属与其它成本项不一致（跨月错账）
- **位置**：`:392`（monthPL writeoffs 用 `substr(created_at,1,7)`）、`:4023`、`:9616`；schema.sql:681-691（**writeoffs 表没有 month 列**）
- **机制**：orders/ledger/payables 都有 month 列 + 触发器，只有 writeoffs 没有 → 4 月 1 日核销 3 月旧单，核销落 4 月、单子落 3 月 → 3 月利润被高估、4 月被低估。月末月初核销是高频操作。
- **改法**：给 writeoffs 加 month 列 + 触发器 + 回填（按 created_at 回填，语义与现状一致）；写入处显式带订单所属月。
- **代价**：需迁移；历史月份归档数字会被「修正」，UI 要提示。

### C3【高】/tax-by-party 的净额算法与 taxNet 不一致
- **位置**：`:10537-10548`（一律 `net = price - tax_amt`）vs `:128-139` `taxNet`
- **现象**：不含税单 price=113、税率 13% → taxOf 得 13.09，taxNet=113；但 /tax-by-party 给出 113-13.09=99.91，**与应收详情差 13.09**。
- **改法**：改用 `taxNet(kind, tax_amt, price)`，SQL 带上 tax_kind。

### C4【高】手工税额可大于含税总额 → 净额为负
- **位置**：`:128`（taxOf manual 直接胜出）、`:11326`（写单只 clamp 税率 0..100）

### C5【高】口径标签与算法不符（同一指标两种标签）
- **位置**：`:9849`（周报自称权责口径但值是三扣公式）、`:14859`（year-summary 未扣核销）、`:9193`（/books 字典说 profit 是「收付实现制」但用的是 pl.profit 权责值）、`:9294` `totals.profit = pl.profit`

### C6【高】账龄分桶 5 桶 vs 4 桶两套标准

### C7【中】writeoff 未结公式缺 COALESCE(paid) → 单据在报表里凭空消失
- **位置**：`:19871`（`price - paid - round2(num(o.wo))`）、`:9799-9853` weeklyStat、`:14960-14990`
- **机制**：老数据 paid 若为 NULL → `price - NULL - 0` = NULL → WHERE 条件为 NULL → **整张单被过滤掉**，SUM 也忽略它。
- **改法**：统一 `COALESCE(price,0)-COALESCE(paid,0)-COALESCE(written_off,0)`；写路径用 `COALESCE(paid,0)+?`。

### C8【中】现金口径排除的 ref_type 集合两处不同

### C9【中】profit-compare 的 expCash SQL 自相矛盾

### C10【低】「逾期风险额」文案比实际桶多含一档

## D 组 · 可靠性（cron / 备份恢复 / 月结锁 / D1 限额）

### D1【严重】月结锁只覆盖 73/195 个写路由
- **位置**：未检查的典型：`:4638` /import-rows、`:4716` /recon-save、`:5326` /pipeline-summary、`:3900` POST /prepaids、`:3911` PATCH/DELETE /prepaids、`:11864` /fixed CRUD、`:16932` /book-reset、`:18140` trash purge
- **机制**：月结锁靠每个写接口手工调 isMonthLocked，漏一个就破防。`DELETE /prepaids` 会删掉**已锁定月份**里的 amort 流水（只看 ref_type 不看 month_lock）→ 归档数字与实时对不上。
- **改法**：把月结锁提到统一写入口（中间件按 body/query 的 month 判定，DELETE 类按被删记录所属月判定），显式列出允许写锁定月的白名单。
- **代价**：改动面大，须分批灰度。**这是小工厂最在意的「这个月到底赚了多少」**。

### D2【严重】备份分片读取无完整性校验 → 缺片静默截断
- **位置**：`:18852-18858`（readBackupContent 拼接 backup_parts）
- **现象**：缺一片 → 字符串少一截 → 恢复出**不完整数据且不报错**；`:19048` restoreCore 只校验 orders/payables/ledger 非空 + version。
- **改法**：backup_parts 加 `seq/bytes/sha256`；读取时核对分片数与 sha256，缺片直接拒绝恢复。

### D3【严重】恢复是 50 条一批的非原子多批事务
- **位置**：`:19039`（runBatch 每 50 条一批）、`:19048-19184`（先 DELETE 三张主表再逐行 INSERT）
- **现象**：中途失败 → 主表已清空，靠 restoreRollback(:19186) 回放快照；回放再失败只回一句「自动回滚失败」，库处于半恢复状态且无工具修复。
- **改法**：① **恢复前先完整校验备份**（所有表行数与列数通过再动数据），把失败概率从执行期挪到执行前；② 回滚失败时把「可重放的恢复指令」JSON 落盘到 backups 表。

### D4【严重】备份中某表为空数组会「清空」该表
- **位置**：`:19048-19184`（额外表循环 DELETE + INSERT）
- **机制**：空数组既可能「真的没数据」也可能「没备份到」，语义混用。
- **改法**：备份格式升级 v3→v4：`tables: {t:{rows:[],count:0,present:true}}` + `missing:[...]`；missing 的表跳过保留现状并 warn。
