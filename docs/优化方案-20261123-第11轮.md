## A 组 · 鉴权与夺权（最高优先级，窗口真实存在）

### A1【严重】`/auth/setup` 公开可抢注：谁先设口令谁当老板
- **位置**：`backend/index.js:1074`（`/auth/setup`）、`:1556`（公开页早退分支含 `path.startsWith('/auth/')`）
- **机制**：早退让 `/auth/setup` 完全绕过鉴权中间件；该函数只判 `if (existing) return 400`，**没有 clientIp / authLocked / authFail、没有安装令牌**。库里还没有 `access_key` 时，任何人 `POST /auth/setup {key:"我的口令"}` 立刻成为老板。上一轮刚让演示入口常显、审核员不再必须先设口令，但老板第一次点「设个口令」的时间窗是真实存在的（尤其部署后到老板首次打开之间）。
- **改法**：①复用已有 `authLocked/authFail/authOk`（:841/:861）加 IP 维度限流（错一次/抢注尝试计数，10 次锁 10 分钟）；②一次性安装令牌：部署时由 `deploy.yml` 生成一个随机 `INSTALL_TOKEN` 写进 step summary（只有老板能看到），`/auth/setup` 必须带它；本地/dev 首次安装可通过环境变量或一个「本机不受此限」的显式开关放行。③给 `_keyCache` 加写后失效（已有 `invalidateKey`）。
- **代价**：多一步「从 CI 摘要取安装令牌」，老板首次设置略麻烦；需兼容已有库（已有 `access_key` 完全不受影响）。
- **验证**：新库无令牌 `POST /auth/setup` 返回 401/400 且不落 `access_key`；带正确令牌成功；连续错 10 次令牌 429。

### A2【严重】`/auth/setup` 并发首设双 INSERT → 500，且恢复码可能提前泄露后失败
- **位置**：`backend/index.js:1074-1086`
- **机制**：`getKey(db)` 走 15s `_keyCache`，两个并发首设请求都可能读到「无口令」，随后裸 `INSERT INTO settings (key,value)` 不带 `INSERT OR IGNORE`，一个成功、一个撞主键 500；恢复码 `saveRecoverCode` 在 `access_key` 写入之后，抢占失败方可能已经拿到了一个后来被覆盖的恢复码。
- **改法**：`access_key` 写入改 `INSERT OR IGNORE` + `changesOf` 判断，0 行时直接返回 400「已设置」（不生成/不回显恢复码）；把 access_key 写入 + recover_code 生成放进一个 `db.batch`，保证同生共死。
- **代价**：低，只影响首次并发。
- **验证**：并发两次 `POST /auth/setup`，一次 200、一次 400（无 500），恢复码唯一且有效。

### A3【严重】`/auth/recover` 恢复码用后不轮换 → 同一码可反复改口令锁死老板
- **位置**：`backend/index.js:1239-1275`（成功路径 :1269-1270）
- **机制**：重设成功后只删 `recover_fail` / `recover_lock`，**没动 `recover_hash`** → 拿到纸条/截图的人可以无限次用同一串恢复码把口令改回去，与老板打拉锯战。
- **改法**：重设成功后立即 `saveRecoverCode(db)` 生成新码（新码只显示这一次、前端提示抄写），或至少把旧 hash 作废（删除 `recover_hash` 并要求老板重新生成）。二选一需产品确认；推荐「轮换 + 一次性显示」。
- **代价**：老板重设后必须更新纸上/密码管理器里的恢复码；前端 `doRecover` 要展示新码页。
- **验证**：同一恢复码第一次成功、第二次返回 `no_recover` 或 `bad_code`。

### A4【严重】`/auth/recover` 试错计数是全局值 → 陌生人 8 次错码就能锁住真主人（DoS）
- **位置**：`backend/index.js:1256-1262`，整段无 `clientIp` 变量
- **机制**：`recover_fail` / `recover_lock` 是 settings 里的**全局**单行值，任何人从任何 IP 猜错 8 次就把全局锁死 10 分钟 —— 老板本人拿着正确恢复码也进不来。
- **改法**：计数改 IP 维度（复用 `authFail` 的 `auth_fails` 表 + `clientIp(c)` + `authLocked`），全局计数只做兜底告警；或新增 `recover_fails` 表按 IP 记。
- **代价**：多一张表或复用现有表；需确认 Cloudflare 的 `clientIp(c)` 只读可信头（防止伪造 IP 绕过）。
- **验证**：A IP 猜错 8 次锁 10 分钟，B IP 拿正确码仍能进；真主人不受影响。

### A5【高】`/auth/super`、`/auth/super-state` 无爆破限流、无审计
- **位置**：`backend/index.js:9788-9822`（`/auth/super`）、`app.post('/auth/super-state'…)`；对照 `/auth/change` 的 :1106/:1110 锁调用齐全
- **机制**：两路由接受 body.key / x-access-key 验证主口令或超级口令，但**完全不调 authLocked/authFail/authOk**，失败也不写 audit_log；又因为 `:1556` 的 `/auth/*` 早退，全局中间件也兜不住 → 攻击者可无限猜口令。超级口令最短仅 6 位。
- **改法**：与 `/auth/change` 同构：入口 `clientIp(c)` 查 `authLocked`，失败 `authFail`，成功 `authOk` + `logAudit`。`/auth/super-state` 若只读状态也要限流（它能探测口令是否设置）。
- **代价**：低，复用现成函数。
- **验证**：连续 11 次错误 key → 第 11 次 429；正确 key 重置计数；失败进 `auth_fails` 与 audit_log。

### A6【高】`POST /attachments` 缺 `attRefVisible` → 员工能给不可见单据挂附件
- **位置**：`backend/index.js:2001-2042`（GET/DELETE `/attachment/:id` 有 `attRefVisible` 校验，POST `/attachments` :2001 起没有）
- **机制**：员工用自己的 PIN 登录、配了 `selfOnly/scopeOwn`，读侧被 `attRefVisible` 过滤，但写侧不校验 → 遍历 id 就能把照片挂到别的员工的客户订单/供应商应付上（数据已写，只是读不出来）。
- **改法**：POST 写库前 `if (!(await attRefVisible(c, db, refType, refId))) return 403`，与 DELETE 一致；`attRefVisible` 内部 catch 改 fail-closed（异常一律 deny）。
- **代价**：低，无老数据迁移。
- **验证**：员工 A 对不可见订单 POST 附件 403；可见订单仍 200。

## B 组 · 账务正确性与口径（会算错钱，第二优先级）

### B1【严重·真 500】`/quick` 三个支出分支 `quickBy` 未定义
- **位置**：`backend/index.js:13495`（`const quickBy = act(c)` 定义在 `if (/收/.test(s))` 块内），引用点在 :13513 / :13524 / :13529 / :13535
- **机制**：发 `text='付水电100'` / `'付货款供应商100'` / `'工资5000'`（不含「收」但含类别词）→ 走 `else if` 分支，引用块作用域外的 `quickBy` → ReferenceError → 500，什么都没写；而 :13495 之前已 `opClaim`，`qRun` 只捕获 `stmt.run()` 的 rejection，异常在 `qRun` 之前抛出 → `op_dedupe` 的 `ref_id=-1` 坑滞留 60s，同 client_id 重试被判 dup_ok。
- **改法**：把 `const quickBy = act(c)` 提到分支外（:13492 之后）；用 `try/catch/finally` 包住 :13495-13543，异常路径 `opRelease`。
- **代价**：极低，纯作用域修复。
- **验证**：三类文本各返回 ok:true 且 ledger/payables 增 1 行；`op_dedupe` 无残留；同 client_id 并发只记一笔。

### B2【高】`yearBook` 预提口径还认旧 `accrual/cash=1`，漏掉当前 `debt_int/cash=0` 利息
- **位置**：`backend/index.js:16241`（`ref_type IN ('amort','dep','accrual')` 且 `cash=1`）、`:16948-16951`（同一旧口径）；实际预提写在 :4248（`ref_type='debt_int'`, `cash=0`）
- **机制**：跑 `/run-accrual` 生成 `debt_int` 流水后，`/year-book`、`/year-print`、`/year-review-print` 的调整项不含这笔，而 `/year-summary`（:17079）含 → 年报与月报对不上。
- **改法**：:16241 改 `ref_type IN ('amort','dep','debt_int')` 且 `direction='out' AND cash=0`（与主口径一致），兼容历史库若真有旧 `accrual/cash=1` 行则两者并计；:16948 同步。
- **代价**：改历史年报展示，需确认是否一次性迁移老口径行。
- **验证**：造一笔 debt_int，逐月 vs 年度 vs year-book 三者金额相等。

### B3【高】`report-data` 年度累计用裸 `SUM(REAL)` → 与月报 `plOf` 差 1 分
- **位置**：`backend/index.js:4722-4738`（`yAgg` 七个子查询全 `COALESCE(SUM(...),0)`）
- **机制**：月度侧已走 `SUM_MONEY`（按分四舍五入再求和），年度累计仍裸浮点 SUM → 多笔 0.01/0.03 时本年累计与逐月加总差 0.01（第 10 轮 C1 只修了月度侧）。
- **改法**：`yAgg` 里的 SUM 全换 `SUM_MONEY(...)`；writeoff 已按事件月份过滤，保持。
- **代价**：低，只影响显示金额。
- **验证**：构造 n 笔 0.01，本年累计 == 逐月相加精确相等。

### B4【高】`/trend` 是第二套利润公式，漏摊销/折旧/预提/坏账
- **位置**：`backend/index.js:15548-15576`
- **机制**：`profit = 接单 − 材料 − 现金费用`，不含 amort/dep/debt_int/writeoff，且订单金额裸 `SUM(price)` → 有摊销/折旧/坏账的月，`/trend` 利润与 `/dashboard` 的 `plOf` 对不上（第 10 轮 C1 统一了 11 处，这里漏了第 12 处）。
- **改法**：`/trend` 复用 `plOf(db)` 按 month 取 `{profit, profit_cash}`（已有 5 分钟缓存），保留 cash_in；或至少补齐四项并用 `SUM_MONEY`。
- **代价**：图表数值会变（是修正）；`plOf` 缓存命中后性能不降。
- **验证**：选有摊销/坏账的月份，`trend.profit == monthPL.profit`。

### B5【中】`/year-summary` 年度现金科目裸 SUM
- **位置**：`backend/index.js:17073-17094`（六个 `SUM(CASE WHEN … THEN amount ELSE 0 END)`）
- **机制**：订单/核销已换 `SUM_MONEY`，现金收入/支出/费用/折旧/摊销/预提仍是 REAL → 年度每月 profit 与 `plOf` 差 0.01，与 B3 的 report-data 也互不一致。
- **改法**：六个 CASE 汇改 `SUM_MONEY('CASE WHEN … THEN amount ELSE 0 END')`（注意列表达式加括号，第 10 轮踩过没加括号整列缩 100 倍的坑）。
- **代价**：低。
- **验证**：0.01×N 下 `/year-summary` 各月 profit 与 `/dashboard` monthPL 一致。

### B6【高】`/recon-fix-batch`、`/party-merge` 吞掉每笔错误仍 ok:true + opMark
- **位置**：`backend/index.js:5498-5510`（recon-fix-batch 每条 try/catch push `mode:'error'` 仍 `opMark` 返 ok:true）、`:6797-6826`（party-merge step catch 设 counts=-1 仍 `opMark` 返回成功）
- **机制**：DB 写失败（D1 限流、月锁、约束）导致某客户核销没做/某表名字没改，用户按 ok:true 重试时又被 opMark 判 dup_ok → **错误被静默固化**。
- **改法**：统计 error 行数，有 error 时 `opRelease` 并返回 200 带 `partial:true, errors:[...]`（或 207 Multi-Status），opMark 只在无 error 时执行；前端展示逐条错误。
- **代价**：前端需处理 partial 标记；保留已成功部分仍需人工修复（可接受，比静默强）。
- **验证**：注入一条必失败数据（锁月/坏 party），确认返回非纯 ok:true、`op_dedupe` 无完成标记、重试能重新执行。

### B7【中】`opClaim` 后无整段 try/catch/finally，异常后坑滞留 60s
- **位置**：`backend/index.js:3028-3087`（`/payroll/pay`）及 20260 等所有 opClaim 路由
- **机制**：opClaim 之后业务主体若在非 `db.batch` 处抛异常（查询失败、noteFail 失手、写日志异常），`ref_id=-1` 坑留到 60s stale 清理，期间同 client_id 重试被判 dup_ok（钱没记但被当成重复请求吞掉）。
- **改法**：opClaim 后用 `try { 业务主体 } catch(e) { await opRelease(...); throw e } finally {}`，成功路径保持 opMark；逐条 review 哪些路由的「部分成功」应保留坑（如 batch 已成功一部分的不能盲目 release）。
- **代价**：低，但要逐路由核对。
- **验证**：注入一次 DB 异常后重试同 client_id，第二次真正执行而非 dup_ok。

## C 组 · 前端跨账套串账与金额解析（会记错账，第三优先级）

### C1【严重·最重】切账套后重放旧账的离线写 → 跨账套串账
- **位置**：`frontend/pages/index/index.js:338-349`（`enqueueOp` 入队不写 book）、`:360-378`（`flushPending` 取当前 `wx.getStorageSync('book')` 发头）、`:925-931`（`_batchSend` 同）、`:7944-8005`（`switchBook` 只 `setStorageSync('book', id)`，未清 `pending_ops`/`_keyQueue`/`_askingKey`/`_tabSeq`）、`:1006`（onShow `flushPending(true)`）
- **机制**：断网时按「收钱」入队（旧账 book=1），此时切到账套 2，onShow 触发 flush → 旧账待发的收款/付款用**新账的 X-Book 头**发出 → 记到账套 2 的同 id 单据上（两本账单号都从 1 开始 → 串单）。
- **改法**：①`enqueueOp` 写 `op.book = wx.getStorageSync('book')`；②`flushPending`/`_batchSend` 按 op.book 分组发送，或只发「当前 book」的、其余保留并提示；③`switchBook` 同时清 `_tabSeq++`、`_tabReqSeq++`、`_keyQueue=[]`、`_askingKey=false`，并对旧账待发项明确处理（推荐：丢弃并 toast「已丢弃 N 笔旧账待发操作，请切回去重记」——**需产品确认丢弃还是保留**）。
- **代价**：中，改动触及离线队列；需新增「带 book 的待发项」回归。
- **验证**：断网在 book1 入队一笔收款 → 切 book2 → 恢复网络 → 断言 book1 单据收款、book2 无变化，且有明确提示。

### C2【高】退回余款 `Number(...)||remain` → 静默全额退回
- **位置**：`frontend/pages/index/index.js:1811`
- **机制**：`const a = Number((r.content || '').trim() || remain) || remain` —— `1,200` / `1.2万` / `abc` 都 NaN → fallback 成 `remain`（整笔余款），且没有 `a<=remain` 上限校验 → 用户想退一部分，结果全退了。
- **改法**：改 `this.toAmount()`（:324，认千分位/¥/万），解析失败 toast 拒绝（不 fallback），加 `0<a<=remain` 校验。
- **代价**：低。
- **验证**：输「1,200」退 1200；输「abc」报错不提交；输超额被拒。

### C3【高】整户付款裸 `Number` + 固定 once 键
- **位置**：`frontend/pages/index/index.js:2429`（groupPay :2419-2439，`amount: Number(ds.amt)`，来自 wxml:738/946 的 `data-amt`）
- **机制**：`ds.amt` 带千分位/元就变 0；`once:'pay-batch'` 是固定键 → 失败重试复用同一 client_id 被后端幂等吞掉（或 8 秒内两次不同金额付款被吞）。
- **改法**：`toAmount(ds.amt)` + 正数校验；once 键带 `ds.n + amt` 指纹。
- **代价**：低。
- **验证**：金额带千分位正确；失败重试能真正重发。

### C4【中】转账/资产/借款/预提 裸 `Number` 金额
- **位置**：`frontend/pages/index/index.js:9602`（`/transfer`）、`:9162/:9167`（资产）、`:7119/:7124`（借款）、`:7221/:7226`（预提）
- **机制**：金额/费率/月数用裸 `Number()`，`8,000`/`1.2万` 被判空或记 0。
- **改法**：金额走 `toAmount()`；费率/月数抽 `numField(v,{min,max,decimals,label})` 返回 `{ok,value,msg}`，不合法 toast 拒绝。
- **代价**：低。

### C5【中】台账数量/单价裸 `Number`
- **位置**：`frontend/pages/index/index.js:8737` min_qty、`:8750` qty、`:8837` fr_price、`:8875` os_qty/os_price、`:8979-8980` rw_qty/rw_cost、`:9033` pw_qty/rate、`:9094` wd_amount、`:9136` wr_rate
- **机制**：同 C4，带单位/千分位归 0，负数量静默入库。
- **改法**：复用 C4 的 `numField()`，数量拒负、单价拒 0（按字段语义定）。
- **代价**：低。

## D 组 · 前端交互健壮性（弱网与错误态）

### D1【高】口令链路绕开 `req()`，无 client_id / 401 卡 / 离线队列
- **位置**：`frontend/pages/index/index.js:6851-6875`（`changeKey` 原生 wx.request + `r.content.split(/[,，]/)`）、`:6935-6952` `/auth/setup`、`:6958-6984` `/auth/find-book`（失败仍存 ak 继续）、`:2721` doRecover

## E 组 · 备份与恢复可靠性（后悔药本身要可靠）

### E1【高】整块备份 sha256 存了但读时不校验
- **位置**：`backend/index.js:19461`（写时 `sha256Hex(content)` 入库）、`:19458-19465`（`readBackupContent` 中 `if (row.content) return row` 直接返回）、`:19466-19472`（只有分片路径校验 sha）
- **机制**：小于 500000 字节的备份以 `content` 整块存储，恢复时跳过 sha，只靠 `JSON.parse` + core 数组非空判断 → D1 单行静默截断/位翻转若仍是合法 JSON，会「校验通过」但恢复后丢数据。
- **改法**：`row.content` 也用 `sha256Hex` 核对 `row.sha256`；历史备份无 sha 时按「未校验」标记告警而非静默通过。
- **代价**：每次读取多一次哈希（<500KB，可忽略）。
- **验证**：篡改 `backups.content` 但保留 sha，`/backup-get` 与 `/backup-restore` 报 `backup_corrupt`。

### E2【高】`/backup-verify` 恒返回 ok:true（假安心信号）
- **位置**：`backend/index.js:20060`（固定 `ok: true`）、`:20040`（usable 仅由 core 数组决定）
- **机制**：备份缺核心表/损坏时 `usable:false` 但 `ok:true`，运维按 ok 判断就误判「备份可用」。
- **改法**：`ok = usable && sha 校验通过 && 无 failed 表`；drift 超阈值给 `ok:false` 或单独 `healthy` 字段并在前端标红；补 `cli.mjs verify-backup` 命令。
- **代价**：前端若读 ok 显示状态需同步改文案。
- **验证**：构造缺 ledger 的备份调 `/backup-verify`，断言 `ok===false`；正常备份仍 true。

### E3【严重·P0】CLI `restore` 跨账套覆盖数据
- **位置**：`scripts/cli.mjs:87-95`（backups 显示「第N本账」却建议 `restore <id>`）、`:98-109`（`post('/backup-restore',{id,confirm:'覆盖'})` 无 book、无 X-Book）；`scripts/_harness.mjs` 的 `post` 只带 X-Access-Key；`backend/index.js:20071`（仅当 `b.book!==undefined` 才校验）
- **机制**：备份 id 按账套各自编号。CLI 在 backups 里看到第 2 本的 `#5`，在默认 BASE（第 1 本）执行 `restore 5`，后端因请求没带 book 而放行 → 把第 2 本的账盖到第 1 本，前端还显示「恢复成功」。
- **改法**：CLI 加 `--book N`，restore 时 body 带 `book` + header 带 `X-Book`；后端 book 校验改**必填**（缺失 400，要求带来源账套）；backups 提示语带 `--book N`；同时检查 Web 前端的恢复请求是否传了 book（没传一并补）。
- **代价**：中，触及 CLI 与恢复接口；需回归正面恢复流程。
- **验证**：`test-restore.mjs` 加一条「跨本 book 的 id 被拒」；cli 实测第 2 本 #id 无法误恢复到第 1 本。

## F 组 · CI / 迁移 / 部署（事故时的恢复链）

### F1【严重·P0】部署前 DDL 变更不能随 Worker 一起回滚
- **位置**：`.github/workflows/deploy.yml:391-411`（seed+migrate 在 deploy 之前）、`:552-567`（rollback 只 `wrangler rollback`）
- **机制**：seed/migrate 对远程 D1 做 CREATE/ALTER，提交后不可由 rollback 撤销（rollback 只回 Worker 版本）→ 若迁移引入坏索引，回滚后旧版继续 503，无法一键复原。
- **改法**：给每个迁移配 down SQL 或快照恢复步骤；至少让回滚 step 明确输出「D1 schema 变更需手工处理」+本次迁移文件名；高风险迁移先影子库验证。
- **代价**：写 down migration 有维护成本，建议先做「告警 + 人工 Runbook」。
- **验证**：造「迁移成功→health 失败」场景，确认回滚后提示明确。

### F2【高】`d1-seed-schema.mjs` 假成功：含 "already exists" 的失败被当成功
- **位置**：`scripts/d1-seed-schema.mjs:62`（`if (/already exists/i.test(out))` 记成功）、spawnSync 无 timeout
- **机制**：wrangler 非零退出时只要输出任意位置有 "already exists"（如后面某索引重名），整本账标「已补齐」，CI 继续部署 → 演示账裸奔（脚本自述「审核点进去就 503」）。
- **改法**：逐条语句执行（复用 `migrations-lib.mjs` 的 `splitStatements`），仅「该语句本身 already exists」才跳过；spawnSync 加 `timeout:120000`。
- **代价**：约百条语句逐条执行增加部署时长（deploy job 30 分钟上限，够）。
- **验证**：造一条故意失败的 schema（拼错表名但保留已存在索引），确认 exit 1；正常 schema 重跑两次幂等。

### F3【高】RUNBOOK 手动迁移命令必失败（事故时延误）

### F4【中】`check.mjs [4.12]` 迁移干跑漏 `ADD COLUMN` 路径
- **位置**：`scripts/check.mjs:433-435`（只模拟 orders/payables 的 written_off RENAME），漏 `backend/migrations/0002_writeoffs_month.sql:10` 的 `ALTER TABLE writeoffs ADD COLUMN month`

- **代价**：解析 SQL 有复杂度，显式清单更稳。
- **验证**：临时把 0002 的 ALTER 改坏，确认 `check.mjs` 变红。
