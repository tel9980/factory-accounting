# 网页端优化方案 · 第 3 轮（稳定 / 高效 / 便捷）

> 基线：`8964a2e`（线上 `20261125-0130`），`backend/index.js` 24257 行。
> 范围：`/`、`/pc`、`/desk`、`/guide`、`/track`、`/statement-ack` 与 12 个 A4 打印页。
> 本轮**只出方案**，不改代码。每条给位置、现在的行为、后果、改法、代价、怎么验。
> 前两轮（第 18 轮「看得见」、第 19 轮「印出来的纸 / 客户最后一米 / 电脑能动」）已上线，本方案不重复。

---

## 一句话

**能优化，而且这轮的重点不是加功能，是三件事：**

1. **稳定**：有三处「看起来成功了，其实没成」——客户点「确认」看到「收到了，谢谢」但服务端零记录；老板在电脑上连点两下「记上」真的记两笔（我实测 `paid` 从 300 变 600）；20 家对账单里失败 3 家，纸出来只写 17 家，不说是哪 3 家。
2. **高效**：`/desk` 打开一次约 **8 个请求 / 45 条 SQL / 约 4.3 万行读**（估算），按 D1 免费额度 **每天刷 116 次就打满**；而线上页面 **根本没压缩**（实测 `/guide` wire 56172B、`enc=-`），因为 `no-transform` 挡掉了 Cloudflare 压缩。
3. **便捷**：`/desk` 有四处「点了没反应」——`window.open` 写在 fetch 回调里被浏览器拦截（打印、发确认、看报表全中）；老板每天第一句「今天收了多少」数据已经返回了但没画出来；报错说「点刷新再试」而页面上没有刷新按钮。

三条主线，共 **42 条**，其中 21 条是几行代码。

# A 组 · 稳定（「看起来成了，其实没成」）

## A1 客户点「确认」，服务端一条记录都没有 ★最高优先
- **位置**：`backend/index.js:16492`（`/statement-ack` 页面脚本）
- **现在**：`.then(r => r.json()).then(d => … (d.text || '收到了，谢谢！') …)` —— **不判 `r.ok`**。后端 403（链接过期）/ 500 返回的 JSON 里没有 `text` 字段，于是走 `||` 兜底，客户看到「收到了，谢谢！提交时间 2026-11-25 09:41」。
- **后果**：唯一一条会骗**外部客户**的路径。客户以为确认过了，老板以为没回音，月底按「没确认」去催 —— 或者更糟：客户确实点了「有几笔对不上」，页面说「收到了」，而异议根本没落库。
- **改法**：`if (!r.ok) { 显示 d.error || ('没提交成功（' + r.status + '）'); return }`；成功后只认 `d.ok`。对照 `:12872` 报价回复页的写法（`d.ok ? … : (d.error||'没提交成功')`）照抄。
- **代价**：6 行。无接口改动。
- **怎么验**：`test-web-pages.mjs` 加两条：把链接的 `x` 改坏 → POST → 页面必须出现「没提交成功」且**不出现**「收到了」；正常链接 → 出现「收到了」且 `/statement-acks` 多一条。

## A2 `/desk` 连点两下真的记两笔 ★最高优先
- **位置**：`backend/index.js:8664-8666`（`post()`）、`:8701`（`doRecv`）、`:8711`（`doExp`）；文案 `:8599`
- **现在**：每次 `post()` 都现造 `body.client_id = 'desk-' + Date.now().toString(36) + Math.random()…`，两个请求的 `client_id` 不同，后端 `opClaim`（`:303-320`，键 `client_id#kind`）认为这是两笔不同的业务，都放行；按钮不 disable。
- **后果**：**我已实测复现**：1000 元的单，连点两次「记上 300」→ `paid` = **600**。页面自己还写着「同一个按钮连点两下只会记一笔」。唯一兜底是收款 UPDATE 的 `… + ? <= price + 0.005` 守卫（超额返回 409 `stale`），所以只有「一次收满全款」时才拦得住。
- **改法**：①`doRecv`/`doExp` 进来先 `if (BUSY) return; BUSY = 1;` 并 `btn.disabled = true`，`finally` 复位；②`client_id` 改成按「内容指纹」生成（`desk-recv-<单号>-<金额>-<日期>`），30 秒内同内容重发由后端判重 —— 与小程序 `req()` 的 `once + _writeIdent` 同一个思路；③文案改成真话。
- **代价**：约 15 行前端。后端不动（判重机制现成）。
- **怎么验**：`test-web-pages.mjs`：同一内容连发两次（同一指纹）→ 第二次必须 `dup_ok` 且 `paid` 只加一次；不同内容两次 → 两笔都记。

## A3 `/desk` 记支出第二笔永远记不进去（没有 `confirm_dup` 入口）
- **位置**：后端 `:13576-13585`；前端 `doExp` 请求体 `:8717`
- **现在**：同一天、同金额、同分类的第二笔支出，后端返回 409 `{error:'今天已经记过一笔「水电 334」，是又花了一笔吗？', dup:true}`。前端**永远不带 `confirm_dup`**，也没有确认弹窗 → 这笔就是记不进去。
- **后果**：老板的绕法是「改成 381 记上去」——账从此永久错 381 与 334 的差额。这类错账事后极难发现。
- **改法**：`post()` 里判 `d.dup` → `wx.showModal` 式确认（网页端用 `confirm()` 或页面内小条）→ 确认后重发带 `confirm_dup: true`。
- **代价**：约 12 行。
- **怎么验**：同额同分类连记两笔 → 第一笔 200，第二笔页面弹「今天记过一笔，是又花了一笔吗」，确认后 200 且 `/expenses` 两条都在。

## A4 打印页出异常时，客户看到一屏 JSON
- **位置**：`:4158`（`/statement-print`）、`:3386-3387`（`/payroll-print`）、`/order-print`、`/report-print`、`/recon-print` 等同类
- **现在**：`const d = await statementSheetData(...)` 外面没有 try/catch，任何异常冒到 `app.onError` → 返回 `c.json({ok:false, code:'server_error', …})`。客户在微信里点开链接，看到的是一串花括号。
- **后果**：这正是「发给客户看」的页面。已有现成的 `errorPage()`（`:4035-4042`）却只在「主动 return」的分支用得上。
- **改法**：给 12 个打印路由统一包一层 `try { … } catch (e) { noteFail(e, '打印页'); return errorPage({ title:'这张单没生成出来', why:'系统出错了（不是链接的问题）', how:'过一会儿再点一次；还不行就让老板重新发一条。', code:'print_error' }) }`。做法：抽 `withErrorPage(fn)` 高阶函数，逐个套。
- **代价**：新增 1 个 helper + 12 处各 1 行包裹。
- **怎么验**：临时把 `statementSheetData` 改成抛错 → 页面必须返回 `fa-error` 错误页（HTML），**不是** JSON；`content-type` 是 `text/html`。

## A5 批量打对账单静默丢家
- **位置**：`:4205-4210`
- **现在**：`for (const party of parties) { try { sheets.push(...) } catch (e) { noteFail(e, '批量打对账单') } }`，标题只写 `${sheets.length} 家`。
- **后果**：勾 20 家、打出 17 家，老板不知道少的是哪 3 家 —— 那 3 家的对账单这月就漏了，而且看起来一切正常。
- **改法**：收集 `failed: [{party, code}]`，标题写「17 家（另有 3 家没生成出来：宏达、鑫源、老李 —— 过一会儿单独重打）」；一张都没成功时直接走 `errorPage`。
- **代价**：约 10 行。
- **怎么验**：让其中一家必然失败（客户名带特殊字符或临时删掉 `party_profiles` 行）→ 页面标题含「没生成出来」并点名；`test-web-pages.mjs` 断言这行文字存在。

## A6 新机器没设过口令，`/desk` 告诉他「口令不对」
- **位置**：`api()` `:8655-8658`；`showGate` 文案 `:8752`；后端返回 `code:'no_key'` 在 `:1787`
- **现在**：`api()` 对 401/403 一律 `throw new Error('auth')`，把后端的 `code` 和「首次使用请设置访问口令」全丢了；页面只说「口令不对（或换了账套）：重新输一次」。
- **后果**：新老板会以为「我记错了」，反复试；真相是「这台机器还没设过口令」。网页端又没有设口令页（只有 `POST /auth/setup`），也不指路 `/pc` 的恢复码卡。
- **改法**：`api()` 401 时 `return r.json().then(d => { const e = new Error(d.error || 'auth'); e.code = d.code || ''; e.auth = 1; throw e })`；catch 里 `if (e.code === 'no_key') showGate('这台机器还没设过口令：先在微信小程序「我的」里设一个；忘了口令点这里用恢复码重设 →')`；口令卡下加 `<a href="/pc">第一次用 / 忘了口令 →</a>`；tip 删掉技术词「localStorage」。
- **代价**：约 10 行。
- **怎么验**：干净库（未 `POST /auth/setup`）打开 `/desk` → 页面出现「还没设过口令」与 `/pc` 链接，**不是**「口令不对」。

## A7 缺数据显示成「¥0.00」
- **位置**：`render()` `:8754-8760`；`money(n)` `:8643`；`fillForms(null)`
- **现在**：某个接口失败 → `kpi = kpi || {}` → `money(undefined)` → `Number(undefined||0)` → 显示 `¥0.00`；下拉显示「没有还欠钱的单」。
- **后果**：老板看到「逾期 ¥0.00」会以为账收齐了。这是最典型的「假安心」。
- **改法**：`money(v)` 区分「没取到」与「真的是 0」：`if (v === null || v === undefined) return '—'`；卡片副行写「没取到」；`fillForms(null)` 时下拉写「（没取到，不是没有）」。
- **代价**：约 8 行。
- **怎么验**：临时让 `/kpi` 500 → 卡片显示 `—` 与「没取到」，**不出现** `¥0.00`。

## A8 `api()` 没有超时，弱网一直转
- **位置**：`:8655-8661`
- **现在**：裸 `fetch`，没有 `AbortSignal.timeout`。全后端只有 1 处超时（`:6856` 的微信推送），页面脚本 0 处。
- **后果**：弱网下按钮永远「记上中…」，老板以为卡死，再点一次（叠加 A2 就变成记两笔）。
- **改法**：`fetch(url, { …, signal: AbortSignal.timeout(15000) })`，超时给「网太慢，没提交上去（不知道成没成）—— 先点刷新看一眼，别急着重记」。
- **代价**：3 行。
- **怎么验**：临时把超时改 50ms → 页面出现那句提示，且**不**出现「记上了」。

## A9 报错把英文和技术码怼给用户
- **位置**：`errText` `:8673-8678`；`server_error` 文案 `:66`/`:90`
- **现在**：用户看到「连不上：Failed to fetch」「没记上：这张单刚被改过（stale）」「HTTP 500」。
- **后果**：40–55 岁的老板不认识，也不知道下一步点哪，只能打电话。
- **改法**：`errText` 只吐人话 + 下一步（「这张单刚变过 —— 点上面的『刷新』再看一眼再记」），技术码塞进 `title` 属性或 `console.log`；`server_error` 那句改成「把这句话截图发给我」。
- **代价**：约 12 行。
- **怎么验**：`test-web-pages.mjs` 断言 `/desk` 页面源码里不出现 `Failed to fetch`、不出现 `（stale）`。

## A10 模块被关掉后，旧打印链接返回 JSON

- **代价**：约 6 行。
- **怎么验**：关掉「对账」模块 → 打开旧对账单链接 → 得到 HTML 错误页。

## A11 缓存可能给出「几分钟前的数」，页面不说到几点的数
- **位置**：`:69-75`（口令 15s）、`:538` `PL_CACHE_MS = 5*60*1000`（利润 5 分钟）、`:7070`/`:7096`（余额 30s）
- **现在**：三个 `WeakMap` 缓存，跨 isolate 各自计时，页面没有「数据截止时间」。
- **后果**：手机上刚记完一笔，电脑刷新还是旧数；老板以为没记上，又记一遍。
- **改法**：①响应头或返回体带 `cached_at`（现在有 `degraded` 但前端不读）；②`/desk` 顶部显示「数据截至 HH:MM:SS」，超过 60 秒标黄；③`plOf` 缓存时间 5 分钟 → 60 秒（与 `accountBalances` 对齐）。
- **代价**：约 15 行 + 一个缓存常数。
- **怎么验**：连续两次 `/dashboard` → 返回体里 `cached_at` 不变且 `/desk` 显示同一个时间。

## A12 月结快照盖住改账，提示只有一行灰字

## A13 `/desk` 内联脚本没有语法门禁（改坏了没人知道）
- **位置**：`scripts/check.mjs`（只对 4 个文件跑 `node --check`）；`scripts/test-book.mjs:153-160` 只抽 `/pc` 的 script

## A14 月结锁检查与写入之间有竞态
- **位置**：`:13575`（`isMonthLocked` 在 INSERT 之前）
- **现在**：检查与写入分两条语句，中间没有事务，SQLite 层也没有约束。

# B 组 · 高效（一次打开要花多少钱）

> D1 免费额度 **5,000,000 行读/天**。`/desk` 首屏约 4.3 万行（估算），**每天刷 116 次就打满**。这组的目标是把它压到 1/4 以下，同时让线上真的压缩。

## B1 线上页面根本没压缩（实测）
- **位置**：`applyEtag` `:1666` 起，`Cache-Control: no-cache, no-transform`
- **现在**：**实测线上** `/guide` wire **56172B**、`/pc` 52141B、`/desk` 22766B，响应头 `content-encoding` 缺失（`enc=-`）；本地 wrangler dev 是压的（gzip 后约 1/5）。原因：`no-transform` 明确禁止中间层改写，Cloudflare 压缩被挡。
- **后果**：手机流量、首屏时间、CF 出口流量全按未压缩算。`/guide` 28KB 的正文每次全量下发。
- **改法**（推荐 b）：**(a)** 去掉 `no-transform` —— 一行，但 CF 压缩后会摘掉 ETag，304 失效；**(b)** 自己在 Worker 里压：`Accept-Encoding` 含 gzip 且 `body` 是文本、长度 > 1024 时，用 `new CompressionStream('gzip')` 压一遍，`Content-Encoding: gzip`；**ETag 用压缩前 body 算**并自己比对 `if-none-match`（压缩与 304 都保住）。
- **代价**：约 30 行（b）。
- **怎么验**：线上 `curl -H 'Accept-Encoding: gzip'` → `content-encoding: gzip` 且 wire 长度 < 原文 1/3；再发一次带 `If-None-Match` → 304。

## B2 `applyEtag` 对签名页白克隆 + 白哈希
- **位置**：`:1689`（`await res.clone().text()`）、`:1692`（`fnv1a`）、`:1697`（`signedPage`）、`:1701`（`h.delete('ETag')`）
- **现在**：克隆与哈希都发生在 `signedPage` 判定**之前**，然后结果被扔掉。批量 20 页约 130KB 每次白拷一遍 + 白算一遍哈希。
- **改法**：把 `const signedPage = …` 提到最前面，签名页直接 `h.set('Cache-Control','no-store')` 并 `return`，不进克隆分支。
- **代价**：5 行（调整顺序）。
- **怎么验**：`test-web-pages` 断言签名页无 ETag；线上批量页耗时下降。

## B3 `/me` 串行读 8 次 settings（关键路径）
- **位置**：`:6633-6656`
- **现在**：`getStaffKey` → `sealed` → `sealed_at` → `getStaffModules` → `staff_users` → `demoKeyOn` → `demo_builtin_off` → `superKeyOn` → `getKey` → `isDemoBook`，全部 `await` 串行。`/desk` 必须先拿到 `/me` 才发后面 6 个请求。
- **后果**：每条 D1 往返 80–120ms（同文件 `:15549` 的注释自己写着这个数）→ 关键路径白等 300–600ms，而且是**每个**页面打开都等。
- **改法**：一条 `SELECT key, value FROM settings WHERE key IN ('staff_key','sealed','sealed_at','demo_key','demo_builtin_off','super_key','access_key','sign_secret')` 取回，内存里判；`staff_users`/`isDemoBook` 各留一条。
- **代价**：约 30 行（要小心 `getKey` 的 15s 缓存语义别破）。
- **怎么验**：`/me` 耗时下降 300ms 以上；`test-perm` 108 项仍全过。

## B4 `/ar-summary` 六条串行查询
- **位置**：`:11976-12002`（应收）、`:12003-12030`（应付同款）
- **现在**：`open` → `over` → `due` → `add` → `got` → `top`，六个 `await` 串行，彼此**没有任何依赖**。
- **后果**：白等 5×80ms ≈ 400ms，而 `/desk` 首屏就调它。
- **改法**：`const [open, over, due, add, got, top] = await Promise.all([...])`（注意 `q()` 的 bind 各自独立，可安全并行）。
- **代价**：8 行。

## C1 四处「点了没反应」：`window.open` 在异步回调里被拦截 ★性价比最高
- **位置**：`:8802`（openStmt）、`:8810`（sendAck）、`:8820`（bulkPrint）、`:8827`（openReport）
- **现在**：全是 `api(...).then(d => window.open(d.url, '_blank'))`。Chrome/Safari 认为不是用户手势 → 拦截。表现：点「打印勾选的对账单」什么也没发生（有的浏览器只在地址栏右侧闪一下图标）。
- **后果**：老板以为坏了，再点一遍，还是没反应 → 打电话。这是「看起来最像 bug 的 bug」。
- **改法**：进函数**同步**开窗拿句柄，回调里改地址：
  ```js
  var w = window.open('', '_blank')
  api(...).then(function (d) {
    if (!d.url) { if (w) w.close(); return showErr(...) }
    if (w) w.location.href = d.url; else location.href = d.url   // 被拦就本页跳
  }).catch(function (e) { if (w) w.close(); showErr(errText(e)) })
  ```
- **代价**：4 处各 4 行。
- **怎么验**：`test-web-pages` 断言源码里 4 处都是「先 open 再赋值」（正则 `window.open\('', '_blank'\)` 出现 4 次，且 `.then` 里是 `w.location.href`）；真机点一次能开。

# 有意不做（写清楚为什么，避免下一轮又提）

1. **不做完整网页版记账**（开单、改单、批量导入对账）：记账留在小程序，网页端的定位是「看数 + 批量打 + 导表」。理由：网页表单在手机上不如小程序，做两套 UI 必然口径分叉。
2. **不做服务端生成 PDF**：Workers 里跑 PDF 引擎要么体积爆要么中文缺字；现在「浏览器打印 → 存 PDF」够用，且客户能自己选。
3. **不做 PWA / 离线缓存**：CSP 里 `script-src 'unsafe-inline'` 是现有 45 处 `onclick` 的代价，改造成本远大于收益；离线记账会与「幂等键」机制冲突。
4. **不把 CSP 一步收紧到 `script-src 'self'`**：需要把 45 处 `onclick` 全改事件委托 + 7 段内联脚本外置，属独立一轮工程；本轮只保留现有的 `default-src 'none'` + `connect-src 'self'`。
5. **不做 `/desk` 的实时推送（WebSocket/SSE）**：D1 不支持长连接，改用「可见时 60 秒轮询」。
6. **不改 `/desk` 的 innerHTML 渲染方式**：实测只拼 20 行，渲染不是瓶颈；换框架是纯风险。
7. **不做多语言**。
8. **不做「批量发微信」**：需要公众号模板消息资质，且客户不一定关注。
9. **不做自动对账（OCR/银行流水解析）**：属产品能力，不是优化。
10. **不把 `/pc` 与 `/desk` 合并**：一个是「填表/导入/账套」，一个是「看数/催款」，受众与频率不同，合并会让两件事都变难用。
11. **不给打印页加页码**：Chrome 不支持 `@page` 的 margin box 内容，只能靠打印对话框勾「页眉和页脚」，方案里已写进 tip。
12. **不做的还有**：`/track` 加留言功能、客户侧自助对账上传、`/desk` 的图表可视化（现在的数字卡片更适合「一眼看完」）。

# 逐条验证口径

新增/扩展的测试：

- `scripts/test-web-pages.mjs`（现有 116 项）扩展：
  - **假成功**：坏链接 POST → 页面含「没提交成功」、**不含**「收到了」；好链接 → 含「收到了」且 `/statement-acks` +1。
  - **连点**：同指纹两次 → 第二次 `dup_ok`，`paid` 只加一次。
  - **`confirm_dup`**：同额同分类两笔 → 第二笔返回 `dup:true`，带 `confirm_dup` 后 200。
  - **JSON 不外泄**：12 个打印路由强制抛错 → `content-type` 必须是 `text/html` 且含 `fa-error`。
  - **批量丢家**：一家失败 → 标题含「没生成出来」并点名。
  - **`no_key`**：干净库打开 `/desk` → 含「还没设过口令」，不含「口令不对」。
  - **`—` 不是 0**：`/kpi` 500 → 卡片显示 `—`。
  - **弹窗**：4 处 `window.open('', '_blank')` 存在且回调里赋 `location.href`。
  - **压缩**：`Accept-Encoding: gzip` → `content-encoding: gzip`；带 `If-None-Match` → 304。
- `scripts/check.mjs` 新增：
  - **[4.22]** 所有内联 `<script>` 能被 `new Function` 编译（覆盖 `/pc`、`/desk`、`/track`、`/statement-ack`、`/guide`）。
  - **[4.23]** 打印路由必须包在 `withErrorPage()` 里（扫 12 个路由名）。
- 性能基线：新增 `scripts/perf-web.mjs`，对 6 个页面记 `rows_read` 与耗时，与 `scripts/perf-baseline.json` 比（超过 1.3 倍即红）。这样 B 组的收益和回退都能被看见。
- 线上核对：部署后 `check-live` + `curl -H 'Accept-Encoding: gzip'` 看 `content-encoding`。

# 一句话收尾

**这轮 42 条里，最值钱的是 7 条「假成功」和 4 处「点了没反应」**：它们不改变功能，但决定老板信不信这套系统。性能那组决定这套系统能撑多少人用（现在一个老板每天刷 116 次就打满免费额度，而且页面根本没压缩）。
