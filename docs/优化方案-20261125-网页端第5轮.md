## 一页摘要

前三轮修掉的是「该说没算出来，却说成了 0 / 账是清的」。这一轮三个新方向：

1. **稳定：三处「已经算错，但界面一切正常」** —— 折旧重复累加（解锁后永远补不回来，而且页面上那句「解锁后再跑一次会补上」是假承诺）、期初借款导入把批次号写进了 `created_at`（家底按字符串比日期）、期初账户余额清空即变 0 且不看月结锁。
2. **高效：cron 一天把全库重算 12 遍** —— 自检 + 备份 + 12 条清理 DELETE 没有 cron 门控，4 个 cron × 3 本账 = 12 次/天，其中 9 次纯重复；另有 `/desk` 每 5 分钟把 11 个请求原样重打一遍。
3. **便捷：两处「本来应该能用，而其实一直坏着」** —— `/pc` 两个上传框用了同一个 `id="bf"`，所以「换电脑搬家：导入这本账」**从来就没成功过**；`/pc` 的提示只在第 3 块里显示，所以「导出 / 一键初始化」点了像没反应。

## A 组 · 稳定（9 条）

### A1 经营报表「账户余额明细」永远空白（P0）
- **位置**：`backend/index.js:5396`、`:5398`
- **根因**：`const accountBalances = async (db) => { … return list }`（`:7322`）返回**数组**；`/report-print` 里 `const bal = await accountBalances(db)` 之后写 `const accRows = (bal.accounts || []).map(...)` → 恒为 `[]`。
- **改法**：`(bal || []).map(...)`；顺手在页面里加一行合计（等于 `/accounts` 的 `total_balance`），对不上就说明账户有脏流水。
- **验证**：`test-web-pages` 断言 `/report-print` 的「账户余额明细」段里 `<tr>` 数 ≥ 账户数；或断言页面出现 `现金` 这个账户名。

### A2 折旧重复累加，解锁后永远补不上（P0）
- **位置**：`backend/index.js:23927`（循环体 23918–23929），入口 `POST /assets/run-depreciation`（`:23993`），文案 `:23999`
- **根因**：`prev` 已经是「这张资产历史上提过的全部折旧」，`booked` 从 `prev` 起步。循环走到**已提过**的月份时，`INSERT OR IGNORE` 命中 0 行，代码又执行一次 `booked += amt` → 虚高 → 提前触发 `booked >= depCap - 0.01` 退出。
- **后果**：因已结账被跳过的那几个月（`:23920`），解锁后重跑也补不回来；资产少提折旧、当月成本偏低、家底虚高。
- **改法**：`if (changesOf(ins) <= 0) continue`（不要 `+=`）。
- **验证**：建一台 12 万/10 年资产 → 连跑两次 `POST /assets/run-depreciation`，断言第二次 `added === 0` 且 `SUM(ledger.amount WHERE ref_type='dep' AND ref_id=?)` 不变；再断言「`prev + 本次 amount === SUM`」恒成立（现在会超）。

### A3 期初借款导入：`created_at` 落成批次号（P0）
- **位置**：`backend/index.js:16326-16327`
- **改法**：列清单换成 `(…, import_batch)`，或者干脆最后一个绑定改成 `now()`（对照 `POST /debts` `:4478` 是 11 个值含 `now()`）。
- **顺带**：加一条一次性修复 —— `UPDATE debts SET created_at=? WHERE created_at LIKE 'IM%'`（用 `start_date` 兜底）。
- **验证**：导入一行不带开始日期的期初借款，断言 `SELECT created_at FROM debts` 匹配 `/^\d{4}-\d{2}-\d{2}/`；并且 `/networth` 那个月能算进这笔借款。

### A4 改账户期初：清空即变 0，且不看月结锁
- **位置**：`backend/index.js:7379`（`opening !== undefined ? num(opening) : num(a.opening)`），整个 handler 无 `isMonthLocked`
- **后果**：`accounts.opening` 是**全局**期初，每个月都会加上它 → 改一次，历史每个月的现金/家底/账户余额全变；已归档的 `month_archive` 仍是旧数，从此永久对不上（月结锁本来就是为了防这个）。`logAudit` 记的也是请求值。
- **改法**：`opening` 用 `numStrict`，为空或认不出直接 400「期初要填正常数字」；有流水或有任何月份已结账时拒绝改期初（提示「解锁后走『记一笔调整』」）。名字仍可随便改。
- **验证**：`PATCH /accounts/1 {opening:''}` → 断言 400；有流水的账户 `PATCH {opening:9999}` → 断言 400 并说明原因。

### A5 编辑支出/应付金额：认不出就**静默按原值保存**却回 `ok`
- **位置**：`backend/index.js:21523`（`const a = num(amount, l.amount)`）、`:21489`（`round2(num(amount, p.amount))`）、`:21502`（税率 `Math.min(100,…)` 静默夹住）
- **实测语义**：把 800 改成 `1000元整` → `num` 认不出 → 回落到 800 → UPDATE 写回 800 → 返回 `{ok:true}`；`changed` 字段全仓无人读，界面只提示「已保存」。空串会走到 `a<=0` 的 400，所以只治「带文字/全角」这一种。
- **改法**：两处改 `numStrict`，`null` 或 `≤0` 一律 400；税率超范围也 400（`/orders:14120` 已经是这个写法）。
- **验证**：`PATCH /ledger/<id> {amount:'1000元整'}` → 断言 400；`PATCH … {amount:'1000'}` → 断言 200 且 `SELECT amount === 1000`。

### A6 结账前检查自己吞错：查询失败被当成「可以结账」，把月份**锁死**
- **位置**：`backend/index.js:5076/5077/5086/5091`（`closePrecheck` 里 6 个 `.catch(() => ({ n: 0 }))`），`:5090` 的 `biz` 查询；消费方 `POST /month-close`（`:5222-5229`）、`GET /month-end`（`:5231` `ready: pre.can_close && !locked`）
- **后果**：对账差异数/对过账家数/未结清单数任一失败 → 全按 0 → `blockers` 空 → `/month-end` 显示「七件事都办好了」→ 有差异的月份被锁死，之后只能解锁。`biz` 失败还会直接回「这个月还没有任何单据…不用结账」。
- **改法**：改成 `checked: false` 往上抛；`closePrecheck` 有 `checked === false` 时 `/month-close` 返回 500「检查没做完，先别结账」，`/month-end` 显示黄字。
- **验证**：`test-ledger` 里造一次「diff 查询抛错」（用 `FA_TEST_BREAK=close_precheck` 或直接单元断言），断言 `POST /month-close` 返回 500 且**没有**写 `month_lock`。

### A7 家底查询失败按 0 算，cron 还把错的**永久存档**
- **位置**：`backend/index.js:23110`（`netSeries` 七条 `.map(x => x.catch(e => { noteFail(e); return null }))`）、`:23176-23179`（`snapNet`）、`:25068`（每月 1 号 cron「月底自动存档」）、`:23198`（`GET /networth` 返回裸数组）
- **后果**：任一条失败 → 欠款/应收/借款按 0 → `net` 偏大 → `/networth` 页照样显示；cron 再把错数字写进 `net_snapshots`（`note='月底自动存档'`，与正常存档一模一样），之后 `drift ≠ 0`，页面 `:23224` 还会解释成「说明那些老单据后来被改过」。
- **改法**：`netSeries` 收集 `fails` 并随结果返回；`snapNet` 发现 `fails.length` 就抛错、不写快照；`/networth` 在响应里带 `fail` 字段，页面显示「这几项没算出来，别当准数」。
- **验证**：断言 `/networth` 每条都带 `fail`（空表示全好）；断言 `snapNet` 在失败时 `ok === false` 且 `net_snapshots` 行数不变。

### A8 报销冲借支：金额认不出 → **按全额冲**；且没有幂等
- **位置**：`backend/index.js:8020`（`POST /loans/:id/reimburse`）、`:8028`（`let a = num(amount) > 0 ? round2(num(amount)) : remain`）、闸门 `:8040`
- **后果**：①金额填「三百」或留空 → `a = remain` → 把剩下的**一次性全部**冲成成本；②没有 `client_id`/`opClaim`（`/loans`、`/loans/:id/return`、`/advances` 都有）→ 断网重发就记两笔。
- **改法**：金额改 `numStrict`，`null` 或 `≤0` 返回 400「报销金额要填正常数字」（「全额」由前端显式传 `remain`）；加 `opClaim(db, cid, 'loan-reimburse')`。
- **验证**：同一 body 连发两次 → 第二次 `dup_ok` 且 `/loans` 的 `used` 只加一次；`{amount:'abc'}` → 400。

### A9 `/quote-print` 与 `/statement-print` 的**金额列**再查一遍空态
- **位置**：`/quote-print` 明细表（`:13280` 一带）、`/statement-print`（`:4200` 一带）
- **说明**：第 21 轮修过「0 印成空白」的一批（`cnt`/`profit`/`deduct`），但报价单明细与对账单的「核销」列还有 `${x.wo ? money(x.wo) : ''}` 这类写法（0 与「没有」含义不同，报价单里 0 折扣应该印 `0.00`）。**这条要人工逐页过一遍**，然后写进 `check-demo-pack` 式的形状断言。
- **验证**：`test-ledger` P4 段扩展：所有打印页 `<td>` 里出现「空字符串」的地方必须是「本来就没有这项」，不再是「0」。

## B 组 · 高效（10 条）

> 基线事实：README 记「每账本每天读约 3.3 万行」，D1 免费额度 500 万行/天 → 现在只用 0.7%。所以这一组**不是救命，是别在库长大后翻车**。

### B1 cron 把全库重算 12 遍（P0 效率）
- **位置**：`backend/index.js:25077`（`const chk = await selfCheck(db)`）、`:25086`（`saveBackup({skipIfSame:true})`）、`:25096-25132`（12 条清理 DELETE）；门控只包住了周报/月报/微信提醒（`:25060` 起）
- **耗在哪**：`selfCheck`（`:20665`）orders 扫 4 遍 / ledger 5 遍 / payables 3 遍；`backupSig`（`:22403`）46 张表各 `COUNT(*), MAX(rowid), SUM` 再全库 1–2 遍；12 条 DELETE 扫 8 张日志表 → 单账套单次 1–3 万行；**4 个 cron × 3 本账 = 12 次/天**，其中 9 次纯重复（周一 01:00 两个 cron 同刻，那天 15 次）
- **改法**：三段各加「北京时间日」门控，只让 `'0 16 * * *'` 那次做（照抄 `:25030` 的 `auto_run_day` / `bjDay` 写法）
- **收益**：12 → 3 次，省约 75%（9 次 × 1.5–3 万行 ≈ 15–27 万行/天）
- **风险**：极低（备份本来就有「7 天强制存一份」；`selfcheck_at` 本来就是日粒度）

### B2 `/desk` 5 分钟自动刷新把 11 个请求原样重打
- **位置**：`backend/index.js:9655`（`setInterval(... load(), 300000)`）、`:9236`（`load()`）、`:9648`（切回标签页再来一次）
- **耗在哪**：一次 ≈ **55–57 条 SQL**（orders 被引用约 37 次）、11 个 Worker 请求、15 KB JSON（gzip 5 KB）；8 小时可见 ≈ 96 次
- **改法**：自动刷新只打 `/kpi` + `/due-schedule?type=ar`；`/dashboard`、`/reminders`、`/next-step`、`/flows` 只在打开页面和点「刷新」时拉
- **收益**：单次 55 → 约 12 条 SQL（省 70–75%）
- **风险**：下方卡片显示旧值 → 已经有「最后更新 HH:MM」可以说明

### B3 `/desk` 为了 12 行「最近记的单」，拉了整个 `/dashboard`
- **位置**：`backend/index.js:9249`（`api('/dashboard?month=')`）；`render()` 里 dash 只用 `today_income` 和 `dash.recent`
- **耗在哪**：`/dashboard`（`:12133`）19 条 SQL（`plOf` 13 个标量子查询 + debts/debt_repays/credit_limits/budgets 全表 + 3 条 COUNT + `custOpen GROUP BY` + `ledger ORDER BY id DESC LIMIT 10`），第 4 轮文档自测约 2.5 万行
- **改法**：新增 `GET /desk-recent`（1 条 `today_income` + 1 条 `ledger ORDER BY id DESC LIMIT 12`），`/dashboard` 留给小程序首屏
- **收益**：单次省 0.3–2.5 万行（占一次 load 的 30–50%）
- **风险**：极低（`/dashboard` 不动）

### B4 `/flows` 的 `limit` 是死参数（`/quotes` 同病）
- **位置**：`backend/index.js:21928`（`… ORDER BY l.created_at DESC, l.id DESC LIMIT 300`，全程没读 `limit`）；`/desk` 在 `:9249` 传 `limit=8` 白传。`/quotes`（`:13892` 读了 `lim`，`:13895` 仍写死 `LIMIT 300`）
- **改法**：读 `c.req.query('limit')`（1–300，默认 300）；`limit <= 20` 时跳过那条整月 `GROUP BY`
- **收益**：300 → 8 行、JSON 省约 90%（行数占比小，但零风险）
- **验证**：断言 `/flows?month=…&limit=8` 返回 `rows.length <= 8`

### B5 `/due-schedule` 一次 load 打两遍，且每遍都全表读两张小表
- **位置**：`backend/index.js:18002`（`SELECT party, contact, phone FROM party_profiles`，无 WHERE）、`:18004`（`dunning_log WHERE type=? GROUP BY party`）；同函数里 `party_terms` 已有 30 秒缓存（`:17904`）
- **改法**：这两条照 `partyTermMap` 塞进 30 秒缓存；`/desk` 把应收/应付两次合并成一次请求
- **收益**：≈1000 行/次 × 一天 100 次 load ≈ 10 万行

### B6 `/suggest` 每记一笔就把三张大表各扫一遍
- **位置**：`backend/index.js:13041`（三条 SQL 都是 `WHERE created_at >= date('now','-90 day') GROUP BY …`）；前端在每笔记账成功后调 3 个
- **耗在哪**：EQP 实测 ar 那条 `SCAN orders USING INDEX idx_orders_customer + TEMP B-TREE`、expense 那条 `SEARCH ledger USING INDEX idx_ledger_fixed(ref_type)` —— 90 天条件只能后置过滤，等于整表走一遍
- **改法**：按 book+type 加 60 秒缓存，写单后失效
- **收益**：一天 20 笔 ≈ 20–40 万行 → 近零

### B7 `/reminders` 里有一条只为一句灰字就全表 GROUP BY
- **位置**：`backend/index.js:24553`（`SELECT customer, COUNT(*), MIN(...), MAX(...) FROM orders GROUP BY customer HAVING COUNT(*)>=2`，只喂「N 家老客户很久没下单」）；`:24551`/`:24552` 与 `/next-step` 的 `:6621`/`:6622` **逐字相同**
- **改法**：custR 改走 `idx_orders_created` 的范围扫（或删掉这句灰字）；两条重复抽公共函数；整个 `/reminders` 结果加 5 分钟缓存
- **收益**：单次省 40–60%

### B8 清理 DELETE 用函数包字段，吃不到索引
- **位置**：`backend/index.js:25104`（`DELETE FROM audit_log WHERE substr(created_at,1,10) < ?`），同类还有 `statement_log`/`dunning_log`/`import_log`/`track_log`
- **改法**：条件写成 `created_at < 'YYYY-MM-DD'`（ISO 串字典序 = 时间序），并给 `audit_log(created_at)` 建索引
- **收益**：与 B1 合计 3–8 万行/天，库越长越明显

### B9 六个「往来单位」页各把 orders+payables 全表 GROUP BY 一遍
- **位置**：`backend/index.js:22087`（/contacts）、`:22031`（/profiles）、`:7567`（/party-dups）、`:17127`（/term-gap）、`:4655`（/credit-limits）、`:17479`（/dispute-book）
- **改法**：抽 `partySummary(db)` + 60 秒缓存，六处共用
- **收益**：单页 30–70%

### B10 日志/导出类页面无分页
- **位置**：`backend/index.js:14950`（/audit-logs）、`:19988`（/import-log）、`:3930`（/track-log）、`:20536`（/export）、`:20575`（/credits）、`:20805`（/compare）、`:22896`（/backup-timeline）、`:6451`（/recon-progress）
- **改法**：默认 `LIMIT 500` + 「更多」翻页；`/export` 保留全量但加 `changed_since` 增量参数
- **收益**：单页 1–3 万行 → 500 行

## C 组 · 便捷（12 条）

### C1 `/pc` 两个上传框同一个 id，搬家永远失败（P0）
- **位置**：`backend/index.js:9791`（`id="bf"`，Excel）与 `:9836`（`id="bf"`，json）；`bookIn()` 在 `:10568`、`bankPreview()` 在 `:10229` 都 `getElementById('bf')`
- **后果**：`getElementById` 只返回**第一个**（Excel 那个空框）→「导入到这本账」永远提示「先选一个导出的 .json 文件」；老板以为文件坏了，重导三四次后放弃
- **改法**：json 那个改 `id="bfJson"`，`bookIn()` 读它（`bankPreview` 不用动）
- **验证**：`test-web-pages` 断言 `/pc` 页里 `id="bf"` 只出现一次；用真导出的包跑一次 `/import-all` 到另一本账（手工验收）

### C2 `/pc` 的提示只显示在页面第 3 块
- **位置**：`#msg` 只在 `:9777` 出现一次；`msg()`（`:10361`）写死取它。调用方 `dlSheet()`（`:10530`）、`arcDown()`（`:10536`）、`bookOut()`（`:10555`）、`bookIn()`（`:10566`）、`bookReset()`（`:10576`）都在下面很远的块
- **后果**：点「导出这本账 / 一键初始化」→ 页面无任何提示（浏览器下载栏里其实有文件）→ 以为没成，再点一次（此时备份已经被覆盖）
- **改法**：`msg()` 改成顶部固定 toast（`position:fixed;top:8px;…`，3 秒消失）+ 失败时红条不消失；或按块 id 就近显示

### C3 催款话术少了店名，客户收到像诈骗

## 有意不做（8 条，附理由）

1. **小程序 `refresh()` 一次刷 6 个接口**（`frontend/pages/index/index.js:1164`，`/dashboard` 19 条 SQL + `/reminders` 25 条 + `/next-step` 7 条 + `/me` 17 条）：这是**小程序**，本轮只做网页端；但它才是真正的大头（一天几十次），建议单独一轮做「轻刷新」+ 30 秒 isolate 缓存。
2. **`/kpi` 的 19 个标量子查询合并成一条 GROUP BY**：本地库 orders 只有 52 行，测不出差别，改完风险大于收益；等有真实规模库再动。
3. **`/desk` 与 `/pc` 抽公共 JS**：实测两页脚本 40 字片段重叠仅 **0.3%**，抽文件没收益，反而多一个请求。
4. **页面体积优化**：`/desk` 61 KB（内联 JS 37.5 K）、`/pc` 67 KB（44.1 K），gzip 后 21.9 / 21.2 KB，已实测 304 生效 —— 不值得再压。
5. **把 `/desk` 改成 SPA 或加 Service Worker 离线**：记账有并发和幂等的硬约束，离线队列会把「哪些写成功了」变成猜；现在 `/desk` 每个写操作都有 `client_id`，重新加载就恢复真值，这个性质比离线更重要。
6. **`INSTALL_TOKEN` 流程重做**：首次设口令要不要令牌是**部署决策**（公开演示 vs 私有部署），不是优化项；只在文案上说明「卡住了问部署的人」。
7. **`saveArchive` 加事务**：D1 没有多语句事务，现在是 SELECT→UPDATE/INSERT 两步（`:4991-4993`），靠 `month TEXT UNIQUE` 兜底；改成 `INSERT OR REPLACE` 更稳但会掩盖并发，留作下一轮连同「结账并发」一起设计。
8. **存疑三条先不动**：`/import-rows` 分块写入中途失败（`:16111-16119`）、`plOf` 5 分钟跨 isolate 缓存、`/reminders` 的 stale 逐单查 `process_log` —— 都需要先做实验确认影响面。
