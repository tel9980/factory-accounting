## A 组：钱算错 / 静默假数据（后端）

### A1 `/kpi` 趋势数组的「收/付/利润/毛利率」恒为 0【高危·已核】

- 位置：`backend/index.js:21256-21260`（SQL，`cin`/`cout` 都查了）、`:21267`（map 只留 `c`/`ad`）、`:21288-21290`（取 `lx.cin`/`lx.cout`）
- 机制：`for (const x of rowsOf(lTR)) lMap[x.mk] = { c: num(x.c), ad: num(x.ad) }` —— 四个列只搬了两个。后面 `const cin = num(lx.cin), cout = num(lx.cout)` 永远 `undefined → 0`，于是 `pf = round2(cin - cout)` 恒 0、`margin` 恒 0。
- 后果：`/kpi` 的 6 个月趋势里，每月「收」「付」「利润」「毛利率」全是 0，只有成本有数。老板看到的是「半年一分钱没收没付」，不报错、不降级、`degraded` 也是空的。
- 改法：`lMap[x.mk] = { c: num(x.c), ad: num(x.ad), cin: num(x.cin), cout: num(x.cout) }`；顺手把这条 SQL 的 4 个裸 `COALESCE(SUM(...))` 换成 `SUM_MONEY`（见 A6）。
- 代价：1 行 + 4 处 SUM_MONEY；建议加 1 条回归（造两个月流水，断言 `trend[i].cash_in > 0` 且 `profit = cash_in - cash_out`）。
- 验证：造一笔本月现金收款 1000，`/kpi` 趋势里本月 `cash_in` 必须 1000、`profit` 与 `/dashboard` 的 `month_profit` 一致。

### A4 三条写路由漏了月结锁，能改/删已结账月份的数据【高危·已核】

- 位置：`backend/index.js:7179`（`POST /orders/:id/apply-advance`）、`:7251`（`POST /payables/:id/apply-advance`）、`:7479`（`DELETE /loans/:id`）
- 机制：两个 apply-advance 都会 `UPDATE orders/payables SET paid=…` + `UPDATE advances SET used=…` + `INSERT ledger`，全函数没有 `isMonthLocked`；`DELETE /loans/:id` 直接 `DELETE FROM loans` + `DELETE FROM ledger WHERE ref_type='loan'`，而同表的 `POST /loans`(:7375)、`reimburse`(:7409)、`return`(:7436) 都有锁。
- 后果：月报是按表实时重算的（`/month-archive` 走 `snapOf` 现算），事后改一笔已结账月的 `paid`，那个月的应收余额、账龄、月报全跟着变，而锁还在——老板看不出被人动过。删借支能删掉已结账月的现金流水，账户余额与银行对不上。
- 改法：两个 apply-advance 读完 `o`/`p` 后加 `if (await isMonthLocked(db, String(o.month || o.created_at || '').slice(0,7))) return 403`（**按单据月判，不是按流水月**，因为 ledger 记的是 `now()`）；`DELETE /loans/:id` 删之前用 `String(l.created_at||'').slice(0,7)` 过锁。
- 代价：3 处各 2 行。
- 验证：结账锁 2026-09 → 对一张 9 月的单调 apply-advance 必须 403；删一条 9 月的借支必须 403。

### A5 固定资产：购置不判月结锁，删除留一堆孤儿折旧【中危·已核】

- 位置：`backend/index.js:21622`（`POST /assets`）、`:21648-21652`（`DELETE /assets/:id`）、`:21656`（`bookDepOne` 从购入月一路补提到 `toM`，遇锁 `continue` 并记 `locked`）
- 机制：
  1. 购置：`buy_date` 只走 `toIsoDate() || now()`，可以填到已结账的月份；折旧是**下一次** `runDepreciation`（cron 每日，`:23199`）从购入月一路补提，非锁月会被写进历史月份 → 已经归档/发给老板看过的历史月利润会变；锁月则永久少提（只在 run-depreciation 的返回里报一句 `locked_months`）。
  2. 删除：`DELETE FROM assets` 只删设备行，**`ledger` 里 `ref_type='dep'` 的折旧流水一条都不删**。删完这台设备的折旧永远留在成本里，`ref_id` 指向不存在的资产，页面上再也找不到它。
- 后果：①购置填个老日期 = 悄悄改历史报表；②删设备后利润永远少一块，且没有任何地方提示。
- 改法：
  1. 购置时若 `buy_date` 的月份 < 当前月：返回一个 `warn`（「这台设备会从 X 月起补提折旧，那几个月的历史报表会变；已结账的月份不会补，会少提 N 个月」），并要求前端二次确认（`confirm: true` 才写）。
  2. 删除时先查该设备的 dep 流水：有则改为「软删」——写 `disposed_at` + `dispose_amount=0`（或加 `deleted_at`），折旧自然停在处置月；真要物理删，必须把 dep 流水一起删且**有非锁月约束**，并在 `logAudit` 里记清楚删了几条。
- 代价：购置 ~15 行（含前端确认）；删除 ~15 行（含审计）。
- 验证：①资产买在上上月 → 返回 warn，且 `runDepreciation` 后那两个月各多一条 dep；②删一台提过折旧的设备 → `ledger` 里该设备的 dep 不再参与成本（或已随删除清掉），`/selfcheck` 无孤儿 dep。

### A6 裸 `SUM()` 收敛（金额合计统一走 `SUM_MONEY`）【中危·已核】

- 位置（仍是裸 SUM 且是金额的，按重要性）：`backend/index.js:21256-21260`（`/kpi` 趋势，A1 顺手）、`:13762-13790`（`/statement-pack` 期初/本期五组）、`:1511-1515`（`accountBalances`）、`:1572-1573`（健康检查未收/未付）、`:2072`（供应商汇总）、`:2832`（订单额）、`:3089`（借支余额）、`:3331-3347`（`/churn-risk` 剩余几条）、`:3457-3463`（`/party-items` 汇总）、`:3645-3657`（风险清单）、`:4187`（`SUM(MAX(0, …))`）、`:16040`（`/trend` 的 dep）
- 机制：SQLite 的 `SUM(REAL)` 是逐行浮点相加，几百行之后会留 0.01 尾差；`SUM_MONEY` 走 `ROUND(x*100)` 整数累加再除。第 10/16 轮已经把报表主链路换完了，剩下这些是「页面/体检/清单」类的出口。
- 后果：同一笔钱在两个页面差 1 分；`/selfcheck` 的对账断言偶尔红一下又自己好。
- 改法：按上面的清单逐个换成 `SUM_MONEY('expr')`（表达式必须带括号），`COUNT(*)`/`SUM(qty)` 不动。
- 代价：约 40 处、机械替换，~1 小时；风险低（只改聚合写法）。
- 验证：`grep -n "SUM(" backend/index.js | grep -v SUM_MONEY` 剩下的命中里，凡是金额列都已包进 `SUM_MONEY` 或加注释说明为什么不用；跑一次 `test-numbers`。

### A8 「batch 内取刚插入 id」有两套互斥写法与相反注释【中危·已核】

- 位置：`backend/index.js:4029`（`/debts` 用 `last_insert_rowid()`，注释说可靠）、`:7149`（apply-advance 抵扣，注释说 `last_insert_rowid()` 在本 batch 内可靠）、`:7396`（`/loans` 用 `(SELECT MAX(id) FROM loans)`）、`:12274`（`/receive` 注释写「last_insert_rowid() 不保证 → 改成 MAX(id)」）

## B 组：吞错 / 假安心（后端）

### B1 四处把 `accountBalances` 的失败当成「账上 0 元」【高危·已核】

- 位置：`backend/index.js:3330`（`/cash-forecast` 的 `jobs` 里 `.catch(() => [])`）、`:6091`（`/next-step`）、`:9334`（家底/资金页）、`:16702`（年报侧）
- 机制：`/cash-forecast` 自己的 `P()`/`PA()` 都会 `failed.push(1)` 并在文案里说「这次没算出来」，唯独账户余额这一条不记 → `cash=0`、`failed.length===0` → advice 走 `safe < 0` 分支，输出「这 14 天要付 X 元，账上只有 0 元，差 Y 元，先把 Z 的催回来」，还回 `failed:false`。`/next-step` 同理推「这周的钱可能不够付 / 账上 ¥0」。
- 后果：假警报，而且是最容易让人做错周转决定的那种——老板可能真的去催款或推迟付款。
- 改法：四处统一 `(e) => { noteFail(e, '账户余额'); failed.push(1); return [] }`（`/cash-forecast` 与 `/next-step` 的返回加 `failed` / 降级提示）。
- 代价：4 处各 1-2 行 + 前端一行提示。
- 验证：临时把 `accountBalances` 的 SQL 改错，`/cash-forecast` 必须回 `failed:true` 且文案是「没算出来」，不能是「差 Y 元」。

### B3 `noteFailDb` / `noteQuiet` 写 error_log 不 await【中危·已核】

- 位置：`backend/index.js:216-224`（`noteFailDb`）、`:230-240`（`noteQuiet`）——两处都是 `db.prepare(...).run()` 裸调，无 `await`、无 `waitUntil`
- 机制：Worker 在响应返回后可能立刻冻结 isolate，未决的 D1 写入会被丢弃。对比 `:20-32` 的 `logError` 是 `await` 的（`:56/:70/:81`）。
- 后果：后台任务失败（定时备份、月报包）和「首页静默降级」这两类最需要留痕的记录可能一条都不落库——正是「线上怪怪的但查不到原因」的那一半。
- 改法：两处改 `await`（`noteQuiet` 在 `/dashboard` 里本来就是 async 上下文）；cron 里 await 会略拉长执行时间，可接受。
- 代价：2 行。
- 验证：故意让 cron 备份失败，`/error-log` 必须能看到那条 `CRON` 记录（连续跑 3 次都在）。

### B4 `error_log` 把查询串原样存 300 字符【低危·已核】

- 位置：`backend/index.js:29`（`params: String(u.search).slice(0,300)`，`ref` 取 `?ref=`/`?client_id=`）

- 代价：3 行。

## C 组：前端（用户会看到假的正常 / 记错月份 / 丢单）

### C1 `role` 初值就是 `'owner'`，`loadMe` 又没有 fail → 员工弱网进首页看到老板界面【高危·已核】

- 位置：`frontend/pages/index/index.js:203`（`role: 'owner'` 初值）、`:7558-7568`（`loadMe` 只有 success）、`frontend/pages/index/index.wxml` 中 **30 处** `role!='staff'`
- 机制：`/me` 超时/断网时 `role` 停在 `'owner'`，30 处判断全部放行；`loadMe` 的 success 里还有一层 `d.role === 'staff' ? 'staff' : … : 'owner'`（默认老板）。
- 后果：员工手机弱网 → 老板界面（成本/毛利/家底/年结/改删按钮），点下去后端 4xx。数据不会漏（后端有闸），但体验与信任成本很高，而且员工会以为「我能看但点不动」。
- 改法：`loadMe` 加 `fail: () => this.setData({ role: 'unknown' })`；wxml 的 owner-only 块从 `role!='staff'` 改成 `role=='owner'`（30 处一次性替换）；`role==='unknown'` 时顶部显示「身份没确认 · 重试」（复用 `_err` 机制）。
- 代价：1 行 + 30 处条件 + 一个提示块；无后端改动。
- 验证：断网启动 → 顶部提示「身份没确认」，成本/毛利卡不出现；恢复网络点重试 → 正常。

### C2 收清 / 转账 / 还款 都不传日期，后端支持却永远落「今天」【高危·已核】

- 位置：前端 `frontend/pages/index/index.js:9981-10015`（`settleAll`）、`:9941`（`addTransfer`）、`:7386`（`repayDebt`）、`:3832`（`_afterPay` 第二笔）；后端都收 `date`：`/orders/:id/receive`（`const { amount, date, account_id }`，`badDate` 校验 + `payLockMonth(date)`）、`/debts/:id/repay`（`:7409` 一带 `const date = String(b.date || now())`）

## D 组：CI / 发布链路（这一组最要紧）

### D1 「体检没过就自动回滚」是死代码，从来没执行过【高危·已核】

- 位置：`.github/workflows/deploy.yml:642-643`（回滚 step 的 `if:`）、`:596-600`（体检步 `bad=true` + `exit 1`）

- 代价：1 行 + `check-live` 输出一个标记；建议加一条 `check.mjs` 门禁：「带 `if:` 且含 `steps.*.outputs` 的 step，必须显式写 `always()` 或某个 status 函数」。

- 机制：默认 `from = 今年 1-1`、`to = 今天`；表名由 `isAp` 三元决定（无注入）。
- 后果：客户多、单据多的账本一次对账打印吃几十 MB 内存（Worker 上限 128MB）；裸 SUM 的尾差靠最后 `round2` 兜，边界可能差 1 分。
- 改法：`bills` 只取对账单需要的 8 列 + 加 `LIMIT`（超了按 A6 的「截断要说人话」口径返回 `truncated`）；五处 `COALESCE(SUM(` 换 `SUM_MONEY`。
- 代价：~10 行。
- 验证：造 5000 张单的客户 → 接口正常返回且带 `truncated`，不 502。

### E4 `wxPush` 子请求数无上限【中危·待确认】

- 位置：`backend/index.js:6497-6540`
- 机制：`SELECT * FROM wx_users WHERE quota > 0` 全表扫后 10 并发发推送，每条 `AbortSignal.timeout(5000)`，成功再 UPDATE；没有分页/总量上限。
- 后果：免费版 Worker 单次 50 子请求、付费版 1000——用户数涨到几十上百后 `0 1 * * *` 的 cron 会中途被杀，后面的用户永远收不到提醒，日志只有一条 subrequest limit。
- 改法：单次上限（如 40 条）+ `settings.wx_push_cursor` 记游标，下一个 cron 接着发。
- 代价：~15 行。

### E5 附件照片进 D1，恢复备份不提示「照片没恢复」【中危·已核】

- 位置：`backend/index.js:2148-2216`（`const bucket = c.env.ATTACH; if (bucket && typeof bucket.put === 'function')`）、`backend/wrangler.toml`（无 `[[r2_buckets]]`）、`BACKUP_NOTICE`（`:20295`）
- 机制：没绑 R2 → base64 直接写 `attachments.b64`（单张 ~650KB、每单最多 6 张）；备份不含照片（公告里写了）。
- 后果：单据照片是 D1 行读写成本 + 2MB 行上限风险；恢复备份后照片全丢，而恢复成功摘要里没有二次确认。
- 改法：短期在恢复成功摘要里明确打印「照片未恢复，共 N 条」（3 行）；中期绑 R2（改 toml + 迁移已有 b64，需一次数据迁移，另排）。
- 代价：短期 3 行。
